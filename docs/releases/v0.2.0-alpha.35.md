# v0.2.0-alpha.35 — A Count That Means One Thing

**Date:** 2026-10-05

## Highlights

- A turn whose commit was refused because less history was loaded than last time is now recorded, and turns already stuck that way are released on the first read.
- Two production Journeys that could not be written to are writable again.
- A Journey stops reading as conflicted forever because of a re-commit that resolved weeks ago.
- A stored conversation is no longer discarded — and its history replaced by whatever is on screen — because a value the app derives disagrees with the copy on disk.
- A cancelled send stops reporting that it still owes Mirror an answer it never produced.

## Where We Started

`alpha.31` bounded the working set to the current chapter, which was the right change and is still the right change. But one field had quietly depended on the old behaviour: the harness checkpoint recorded the length of whatever conversation the application happened to be holding, and before `alpha.31` that was always the complete generation. Afterwards it was the current chapter — unless the Navigator had opened complete history, in which case it was everything again.

So a field that was supposed to describe the conversation began describing the reader's navigation. A commit taken with the chapter loaded, following one taken with all of history loaded, looked like the conversation had shrunk. The reconciliation guard called that a checkpoint regression and refused the commit.

The refusal was the expensive part. It returned without recording the evidence the turn had just established, so the turn's harness body stayed pending permanently and the checkpoint froze — which made every following bounded commit regress too. A turn in that state fails settlement, because the step that builds the Mirror append item requires a committed harness body. Recovery then delivered the content by a different route, roughly forty seconds later, which is what a long `Finishing` had been made of. And because no reason code was ever cleared, twelve of twenty Journeys read as conflicted, nine of them over a re-commit from September.

It had also stopped being invisible. A turn with a pending harness body reports `projection_pending`, which blocks new invocations, so two Journeys could not be written to at all.

## What Changed

### The checkpoint counts committed turns, not loaded messages

The harness checkpoint now carries the number of turns whose harness body is committed. That is monotone by construction, owned by the same record, and indifferent to how much history is on screen. The regression guard reads it. The count is derived where the commit is recorded rather than passed in, so a caller cannot report a number that disagrees with the bodies it is committing.

`messageCount` is kept, because removing it would invalidate every stored record, and is documented as what it always was: the surface length at the time, descriptive, guarded by nothing.

### A refused commit records what the turn established

When a checkpoint comparison fails, the body's evidence is now recorded and the anomaly noted, while the existing checkpoint is left alone so a regression cannot pull one backwards. Contradictory evidence for an already-committed body is still refused — overwriting it would destroy the record of the commit that actually happened.

Turns already stuck in the refused state are committed from the message ids the refusal had already staged, at the point where stored state becomes live state. Every such turn in the production store had both of its messages already saved, checked individually, so this restores a flag rather than asserting a fact.

### A conflict that is over stops being reported as current

Only a reason that says a record is bound to the wrong thing now keeps a Journey conflicted. A re-commit that presented different ids, or a counting anomaly, stays in the Journey's history permanently without pinning its present state. Nothing is deleted; the audit trail is intact and the classification is honest.

### A derived value can no longer discard a conversation

The parse of a stored conversation used to validate its classification against the value the application derives, and reject the whole record on disagreement. A rejected record reads as absent, and an absent record is treated as permission to replace the stored history with whatever is currently loaded.

Three production Journeys were in exactly that state and could not be parsed at all; one of them was carrying a checkpoint that remembered 122 messages over 24 still stored. The classification is now recomputed when the record is read. Recomputing a derived value cannot lose information; rejecting the record that carries it can.

### A cancelled send owes nothing

Interrupting a turn now fails its Mirror body alongside its Pi body, so a send that produced no answer stops reporting delivery debt that recovery is correctly unable to clear.

## Conscious Exclusions

**No live run stands behind this.** The change is verified by replaying the shipped rules against the real production store read-only, by thirteen new guards including one that checks the healing is actually wired into the read path, and by the full gates. No turn was settled by a build containing it. A Dev smoke pass was skipped on purpose: Dev keeps its own data directory and holds none of the damaged records this release is for. The verification that proves it is the production upgrade, and it is owed immediately — the healed count must read zero, the two Journeys must be writable, and no conversation may have lost messages.

**The Mirror checkpoint was left alone.** It has three different producers feeding the same kind of guard. It is the same class of defect and has not been observed failing, so it keeps its own change rather than riding along in this one.

**`messageCount` is now read by nothing.** It was kept so that no stored record needs rewriting. A field no one reads is debt, and removing it is a schema decision for another release.

**The empty chapter file is not fixed here.** A separate planned change addresses a closed chapter that overwrote its own file; it is independent of everything above and is not in this release.

## What We Learned

**A field's meaning can be changed by a feature that never touches it.** Bounding the working set was correct and well tested. What it altered was the meaning of a number recorded somewhere else, and nothing in the system stated that meaning, so nothing could notice it had moved. Six consecutive defects on this path have now all been of that shape: identity is restated and validated everywhere and has never failed, while every question of extent — how many, how far, which part — is duplicated across records with different definitions and enforced nowhere.

**Validation belongs on inputs; derivation belongs on reads.** Checking a computed field against its stored copy reads like rigour and behaves like a trap, because it turns every future change of the rule into a silent discard of durable data. It had already fired, in three Journeys, before anyone went looking.

**Absence and emptiness must not be the same value.** The reason a rejected record is dangerous is that nothing distinguishes "this record could not be read" from "this record is empty", so a refusal on the way in becomes a deletion on the way out. That distinction is still missing elsewhere on the load path and is recorded as the heaviest remaining debt.

**A defect worth fixing first is one that grows while being fixed.** The count of stuck turns read 17 when the problem was captured, 24 when it was implemented and 28 when it was verified, inside a single working session. That rate, not the elegance of the diagnosis, is why this went ahead of other planned work.

## Next Horizon

The production reading comes first and is owed, not optional: confirm the heal cleared every stuck turn, that the two blocked Journeys accept writes, and that no ledger lost a message. Then re-read the `Finishing` tail the previous release instrumented, now that a large part of it is predicted to have been this recovery detour. After that, the empty chapter file, and the audit of every remaining place where a swallowed read error could authorise a write that deletes.
