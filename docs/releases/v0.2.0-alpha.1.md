# v0.2.0-alpha.1 — Governed Alpha Release Candidate

**Date:** 2026-09-08

## Highlights

- Prepares the first governed alpha release candidate for Mirror Desktop.
- Uses the alpha updater overlay and separate alpha updater public key.
- Builds signed updater artifacts and a macOS DMG locally.
- Stages alpha release notes, release index, updater manifest, artifact, signature, and DMG without publication.
- Preserves the explicit boundary around push, tag, GitHub Release, notarization, and endpoint promotion.

## Where We Started

Mirror Desktop had already proven the trusted self-update loop through a private-test rehearsal. That proved the mechanism, but not yet the release posture. The private-test channel was intentionally disposable: useful for learning, not a stable surface for alpha distribution.

The next step was to prepare an alpha candidate that could be reviewed as a coherent release object before anything is published. The alpha channel needed its own updater key, endpoint prefix, release note, staged manifest, and evidence record.

## What Changed

The application version authority moves to `0.2.0-alpha.1` across package, Tauri, and Cargo metadata. The candidate is built with `src-tauri/tauri.alpha-update.conf.json`, which points installed alpha apps at the alpha updater prefix:

```text
https://updates.mirrormind.sh/mirror-desktop/alpha/{{target}}/{{current_version}}/latest.json
```

The alpha candidate is staged locally with the updater artifact, signature, DMG, release note, release index, and manifest paths for alpha current versions. This creates a reviewable release payload without uploading it to the alpha endpoint.

## Conscious Exclusions

- This release candidate is not published to the alpha endpoint.
- No Git tag is created.
- No GitHub Release is created.
- No Git push is performed.
- No Apple notarization claim is made.
- No public production release is declared.
- The updater still targets application bytes only; Mirror homes, `memory.db`, identity, credentials, Journey content, conversations, app data, and Nautilus Harness state remain outside the mutation boundary.

## What We Learned

The first alpha should not be a heroic act of uploading files. It should be a prepared object with a narrow decision point: the artifact exists, the manifest exists, the release note exists, and the channel governance exists — but publication remains a separate act.

That separation makes the release safer. It lets us review the candidate as a release before turning it into an update path for installed apps.

## Next Horizon

The next step is explicit Navigator review of the staged alpha candidate. After review, the Navigator may authorize one or more separate actions: publish the alpha endpoint, create a Git tag, push commits, create a GitHub Release, notarize the app, or keep the candidate local for another iteration.
