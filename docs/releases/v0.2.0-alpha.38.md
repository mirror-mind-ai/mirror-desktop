# v0.2.0-alpha.38 — The Request Keeps Its Name

**Date:** 2026-10-05

## Highlights

- A corrected turn's durable record now names **your request**, not the correction you sent mid-run.
- Work the agent had already produced before you interrupted is no longer discarded from the record.
- Mirror receives your request as the turn's message, where it had been receiving the correction.
- A reloaded conversation shows a correction attached to the answer it changed, instead of standing in as a question nobody answered.
- Verified against the production store: **573 of 573** already-recorded turns still re-derive exactly, so nothing already written becomes unreadable.

## Where We Started

Sending a correction while the agent is working has been supported for several releases. You type a redirection, it reaches the running agent, and the agent takes it into account. That part worked.

What did not work was the memory of it. Every durable record of a corrected turn — the turn journal, the chapter, the item delivered to Mirror — recorded the **correction** as the thing you had asked, and left your actual request belonging to nothing. Across the nine real corrections in the store, this was true in nine of nine. In seven of seven turns checked directly in the Mirror database, the message stored as yours was the correction.

So the conversation remembered that you had interrupted, and forgot what you had interrupted *about*.

Two releases ago this surfaced as something stranger and easier to notice: a reloaded conversation showing a correction where a request should be, and an answer sitting under a question that did not match it. That was the same defect seen from the reading end.

It also explains a standing observation that had never been accounted for — that a correction can sometimes *end* a turn rather than redirect it. When the agent treats a correction as a fresh question, it answers that question and stops. Nothing in the Desktop caused it, and nothing recorded that two exchanges had happened where the harness believed there was one.

## What Changed

### A turn is bounded by the invocation, not by every time you typed

The native projection that reads the agent's session file treated every user entry as the start of a turn. A correction is a user entry, so a correction started a turn — and since the recorded turn is the last one in that reading, the correction won.

The fix turned out to need nothing new. The native side already computed, before every invocation, the entry the previous run ended on. It used that value only to check that something had happened. But a run **is** one invocation, and an invocation starts once, so the request is simply the first thing you said after that point, and the answer is everything the agent said up to the reply it completed. A correction is not the first.

Nothing new crosses the boundary between the app and the agent's session, and no text is interpreted or guessed at. The rule does not need to know what a correction *is*.

### The work before your interruption stops being thrown away

The same reading did something worse than mislabel. On starting a new turn it cleared the prose already gathered, so anything the agent had said between your request and your correction was dropped from the record entirely. Four of the nine real corrections lost text this way — between 55 and 427 characters of real reasoning.

In one case the loss was structural rather than partial: in `livro-lideranca-soberana` the agent had completed a 518-character answer, you sent an 18-character correction, and the agent answered again in 115 characters. The projection made two turns where the harness had one, took the second, and the first answer belonged to no turn at all.

Those answers are now part of the turn they belong to.

### A restored correction points at the answer it changed

On the reading side, a correction recovered from a reloaded conversation was being indexed against a message that was not among the ones drawn, so the correction existed in the data and appeared nowhere on screen. Worse, because the correction was wearing the request's identity, the two had effectively swapped places: the orphaned "question nobody answered" was your own request.

A reloaded conversation now resolves a correction through an anchor when the message it names is not present, and the request takes its identity back by position. Replayed over the store, all eight real corrections are now placed correctly where the first version of this rule placed none of them.

When a claim cannot be trusted — two different turns naming the same correction, say — the surface falls back to exactly today's behaviour. A correction shown as a request is wrong but visible. Honouring an untrustworthy claim would hide a message instead, and that is worse.

## Conscious Exclusions

**The nine turns already recorded wrongly are not repaired, and neither are the seven Mirror messages.** They keep the correction as their request. Repairing them would mean writing attributions into the Mirror database that nothing in the record supports — reconstructing what you meant rather than reading it. That is a separate decision with its own authority, and it has not been taken.

**No corrected turn has settled on this build.** A correction cannot be scheduled; it happens when you interrupt an agent mid-run. So the change rests on unit tests, on source assertions for the parts inside native commands, and on replaying the real store read-only. The observable event is the next corrected turn: its record should name your request, its answer should contain what the agent said before you interrupted, and Mirror should receive your request as the message.

**Dev homologation of a corrected turn is owed and was not performed before this release.** This changes what reaches the Mirror database, and no read-only replay exercises a write. That verification is deferred, knowingly, to the field.

**The answer's extent could not be confirmed by replay at all.** Re-deriving a stored run closes at the last reply in a session file that has since grown by many runs, so the replay over-spans and reports answers many times their real length. At the moment a turn actually ends, the session ends with that run — which is the only moment the rule is used. The extent claim therefore rests on the native tests and on a bounded replay, not on the unbounded one.

**Recovery still cannot segment a corrected run.** The path that repairs a turn abandoned by a crash spans whole sessions and has no invocation boundary to work from, so it keeps the old reading and refuses as ambiguous when it cannot pair records one to one. That limitation predates this release and is not introduced by it, but it is also not fixed.

**The compensation on the reading side is now partly redundant.** Once a release has carried this and a corrected turn has been seen reading correctly from a true record, some of it can come out. It stays until then, because it is currently the only thing making an already-damaged conversation readable.

## What We Learned

**The third answer was better than both options the capture proposed.** One option was to pass the correction's identity across the boundary; the other was to have the native side recognise a correction by inspecting its text. The value that made both unnecessary was already being computed, one line above, and used for something smaller. Looking for what the system already knows beat designing a new channel.

**Compatibility ordered the work, not the fix.** Changing what a turn's identity *is* makes every turn already recorded under the old identity unfindable by the three places that match stored evidence. That constraint, not the correction logic, decided the sequence — and it also simplified the result: one re-derivation of the turn a recorded pair spans reproduces the old shape for an old pair and the new shape for a new one, so the planned fallback was never needed.

**A premise can be wrong in a way that makes the measurement sharper.** The reading-side fix was captured as "a correction cannot find the message it corrected." Replaying it showed the first rule would have refused all eight real corrections and done nothing at all. The actual defect was that the correction and the request had swapped identities, which is both more specific and more serious than what was written down.

**Two of the measurements taken while verifying this were wrong before they were right.** The first compatibility pass reported 196 mismatches — all of them a count, with the text identical — because the script read the session differently from the shipped code. The corrected pass found 573 of 573. That mistake earned a real improvement: the native tests now put a tool result and an unrelated entry on the branch and assert the count exactly, because the component that builds Mirror's item rejects a turn whose count disagrees with what was stored.

## Next Horizon

The correction's record is now true at the source. What remains around it is the reading of a turn that is *not* corrected: whether a finished turn should collapse its detail the instant it stops being the newest, left open two releases ago and still open.

Underneath, the larger debt is unchanged and named in the architecture: absence and emptiness are still the same value across the load path, so a rejection on a read path is a deletion on the next write. Three releases have removed specific instances of that shape. None has removed the shape.
