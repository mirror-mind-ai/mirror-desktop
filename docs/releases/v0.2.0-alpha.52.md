# v0.2.0-alpha.52 — Recovering an Answer That Was Already Saved

**Date:** 2026-10-17

## Highlights

- **A turn that finished while its record did not notice is now recognised**, named, and recoverable without restarting the application.
- **The answer comes back on request.** It was never lost; what was missing was the path back into the conversation.
- **The recovery underneath stopped refusing turns it could repair.** It had refused twelve in a row across five Journeys, recovering none.
- **A later successful turn no longer destroys an earlier stranded one's recoverability**, which is what made the condition permanent.
- **"Nothing left to attribute" and "too many candidates to choose between" are no longer the same verdict.** They were reported under one name.

## Where We Started

The previous release ended with a turn that had answered and then sat on *Finishing* until the application was force-quit. `alpha.51` made that wait legible: it now says why no exit is offered. It deliberately did not end the wait, and said so.

The plan was to add a detector — the application holds a durable record saying the turn is running and a session file holding the finished answer, so recognising the disagreement needs no new source of truth.

Then the production artefacts were read again, and the plan was wrong in its first sentence. **A detector already existed, it had run, it had refused, and it had written down why** — into a file nothing in the application reads. It was there eleven hours before anyone looked.

That changed what this release is. The missing piece was never the noticing. It was that the repair refused.

## What Changed

### The recovery stopped refusing on arithmetic that could not succeed

When a turn's record is stranded, the application tries to match it against the agent's session to work out what actually happened. That matching kept **one high-water mark** — the furthest point in the session any completed turn had claimed — and then required that *every* stranded record in the conversation pair up one-to-one with *every* unclaimed request beyond that mark.

The same real turn broke that rule twice in one day, in opposite directions:

| | |
|---|---|
| **In the afternoon** | two earlier turns had died at the provider, leaving requests nobody ever claimed. One stranded record, three loose requests. Refused. |
| **By evening** | a later turn succeeded and claimed the whole session, including the stranded turn's own request and answer. One stranded record, **zero** loose requests. Refused, and now permanently. |

The repair drops the high-water mark entirely. Each turn's completed work already records *which request it answered* — that information was on disk the whole time, and the single mark was a lossy summary of it. A stranded record is now judged inside its own admission window: the requests asked after it was admitted and before the next turn was admitted. One answered request is the answer. One unanswered request, with a later turn after it, means the turn was interrupted. No request at all now says so in its own words instead of being reported as ambiguity.

Checked against the actual production data, read-only: the turn that was unrecoverable all day is attributed to its own request, with the answer it produced at 13:01:49.

### The application notices, and says which kind of stuck it is

There are two ways a turn can be stranded and they need different sentences. One is *the record finished and this conversation never heard* — already handled. The other is new: *the agent finished and the record itself never heard*, which is what happens when the turn's own bookkeeping freezes seconds before the answer arrives.

To tell a frozen turn from a genuinely long one, the application now reads **the last line of the agent's session file** — nothing more. That line is the current end of the conversation by construction, so the check costs one short read, and it happens only while the record still says the turn is running. An idle Journey and a finished turn never pay for it.

If that final line is a completed answer timestamped after this turn began, and it has been sitting there longer than a settlement could plausibly take, the turn is stranded. The notice says the answer is in the agent's session and that nothing is lost, and offers the same **Recover this turn** button that already existed — which now succeeds, because of the first half of this release.

The guard against false alarms got more attention than the detection. Every state a healthy working turn can be in — mid-tool-call, streaming, awaiting a tool result, compacting — is tested to leave the verdict exactly where it was, however long the turn has been running. **A detector that fires on healthy turns would be worse than the silence it replaces.**

## Conscious Exclusions

- **A refusal is still invisible while it is being made.** The file recording why a recovery declined has no reader, and this release did not give it one. That the reason sat unread for eleven hours is the finding; surfacing it is a separate change.
- **Why the record froze is still unestablished.** This release recognises the outcome and repairs it. It deliberately does not depend on knowing the cause, because comparing outcomes is something it can do today and diagnosing the cause is not.
- **Recovery is still offered, not taken.** The application does not repair a stranded turn unasked.
- **One existing stranded record in a test fixture is left unjudged**, because that fixture feeds one session's data to another session's records — a shape the real recovery never produces. It is noted in the test rather than quietly asserted.

## What We Learned

**Before building a detector, check whether one exists and is refusing.** The planned work was a mechanism to notice this condition. The mechanism was already there, had run, and had declined. An afternoon of scoping went into a premise that one file on disk contradicted.

**A summary derived from durable facts can be worse than the facts.** The high-water mark was computed from per-turn records that each already named the request they answered. Keeping the summary instead of the records is what made two different situations produce the same refusal.

**A mechanism can be entirely non-functional in the field while every test passes.** Twelve refusals, five Journeys, two weeks, zero recoveries — and the tests were all green, because they encoded the rule's mechanics rather than what the rule was supposed to establish. Narrowing those tests was a precondition for repairing the thing they guarded.

**Success can destroy the recoverability of an earlier failure.** The later turn that worked perfectly is what made the stranded one permanently unfixable. Nothing was wrong with that turn.

**One name for two facts hides one of them.** *Ambiguous* covered both "there are several candidates" and "there are none", and the second is not ambiguity at all.

## Next Horizon

Making a refusal visible while it happens. This release repairs the refusals it could measure, but the pattern that found them — a decision recorded in a file nothing reads — is the same shape as the silence `alpha.51` fixed on the surface, one layer down. The question is whether a recovery that declines should say so where the Navigator is, and the answer this programme has given to that question so far has been yes.
