# v0.2.0-alpha.27 — Journeys Start Reliably, Recovery Is Isolated

**Date:** 2026-09-30

## Highlights

- Lets an existing Journey start while unrelated Journeys are working, instead of silently removing its only start action.
- States why a start is waiting — native occupancy, capacity, own-Journey work or runtime binding — directly on the not-started surface.
- Keeps an ambiguous historical turn from aborting delivery recovery for unrelated current work.
- Preserves ambiguous journal evidence without guessing, while recording one bounded diagnostic per changed recovery verdict.

## Where We Started

Fifty-nine of the seventy-seven production Journeys had no dedicated Desktop thread, which is a
normal first-start state. Yet the start action was gated on a global busy flag: work in any Journey
made every thread-less Journey look unavailable, and the only surface available before start gave no
reason for the missing action.

A separate Dev recovery debt exposed a second trap. Two genuinely ambiguous records from a retired
generation aborted the whole recovery loop, preventing a current generation's outbox debt from being
materialized or delivered. The offered repair action could therefore never succeed.

## What Changed

**Journey start is now scoped to real conflicts.** Provisioning asks for a validated Mirror binding
and the selected Journey's native admission, rather than for global silence. Existing capacity
authority still prevents starting when capacity is genuinely exhausted or that Journey already owns
native work. The not-started surface always renders the action; when waiting, it is disabled with a
truthful reason.

**Recovery is per record, not all-or-nothing.** Each stale record is judged using its own Pi
session, generation and thread evidence. A record that cannot be uniquely recovered remains in the
journal untouched, but no longer prevents other records and delivery materialization from continuing.
The resulting Dev debt settled from two pending terminal/outbox states to zero pending outbox items.

**Diagnostics preserve change, not noise.** Skipped recovery verdicts are recorded beside the
outbox, but only when a turn's reason changes. Repeated reconciliation during Journey load no longer
fills the bounded log with the same fact and evicts later evidence.

## Conscious Exclusions

- No automatic creation, reset, replacement or deletion of a Journey conversation occurs merely on selection.
- No recovery invokes a model or guesses at ambiguous Pi evidence.
- A full native Pi capacity remains a real reason to defer starting a Journey.
- This candidate does not publish, tag, push, sign, notarize, promote or mutate updater endpoints.

## What We Learned

A global guard is not automatically safer: when an action owns a specific Journey and capacity
authority already identifies its real conflicts, broad busy state turns safety into exclusion.

Recovery batches need the same authority discipline. A single unclaimable record is evidence about
that record, not permission to make unrelated records unrecoverable. Failing closed must be scoped,
not contagious.

Bounded diagnostics must represent changes of state. A repeated observation is not new evidence, and
recording it as if it were can destroy the signal the bound was meant to protect.

## Next Horizon

The remaining RS021 work stays captured until explicitly pulled. The next release decision is
separate: this candidate requires artifact review and explicit promotion authority before any tag,
push or publication.
