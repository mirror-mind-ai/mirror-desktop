# v0.2.0-alpha.31 — Work From the Current Chapter

**Date:** 2026-10-02

## Highlights

- Opens a compacted Journey on its current chapter rather than rebuilding its complete historical generation.
- Makes earlier history explicit and reachable: one request loads the complete generation when it is needed.
- Names the reader-facing boundary consistently as a chapter across history, navigation and search.
- Stops Segment publication from overwriting durable Conversation metadata and truncating its turn ledger.
- Stores only projection-owned state and keeps new Segment files scoped to their own messages.

## Where We Started

Pi compaction already kept a bounded active context, but Desktop ignored that boundary. Every Journey
open, send preflight and manual compaction rebuilt the complete active branch. On the long-running
`mirror-desktop` Journey, that meant 7,373 projected entries and roughly 51.53 MB reached the
surface even though Pi's current context began after its last compaction.

The historical-history affordance existed but could never appear: every caller supplied it a count
of zero, and its complete-history action simply repeated the reconstruction that opening had already
done. Meanwhile, closed Segment publication overwrote the active durable projection with the current
Segment's payload. The active projection is the only durable turn ledger, so that overwrite kept
shrinking it while the message body continued to reconstruct from Pi.

## What Changed

The native Pi inspection now accepts a working-set scope. The default Journey surface asks for the
suffix beginning at Pi's last compaction `firstKeptEntryId`; structural facts such as the full
compaction count and turn list remain complete. The returned window reports its omitted entries and
chapters, allowing the Desktop to say exactly what is not loaded rather than infer it from what it
has drawn.

On the measured Journey, the current-chapter window contains 286 of 7,373 projectable entries. The
24 earlier chapters remain durable and one explicit request loads the complete generation. Send
preflight and manual compaction retain whichever scope the reader chose, so ordinary reprojection
does not silently widen the working set.

A partial surface cannot be allowed to erase durable history when it saves. Storage now composes the
window with the earlier stored messages, preserving attachment provenance that Pi cannot rebuild,
while still honoring edits and removals within the loaded window. Segment publication no longer
rewrites the active projection, derived Pi maps are not persisted, and per-message maps in new
Segment projections are limited to the messages they own.

The product calls this visible boundary a chapter everywhere. Segment remains the internal storage
and loading term: the manifest, `segment-N.json` files, native scope and domain types retain it
without exposing two names for one reader-facing cut.

## Conscious Exclusions

- No Pi JSONL, Mirror record, Journey identity, run authority or compaction behavior changes.
- No deletion, migration or repair of legacy closed Segment files; they remain compatible history.
- No incremental per-chapter history loading: the explicit request intentionally loads complete history.
- No general transcript virtualization or new search backend.
- No instrumented Journey-open latency percentile is claimed.

## What We Learned

A Segment is useful architecture and a chapter is useful language, but exposing both made a single
compaction boundary look like two concepts. More importantly, working-set bounds must be enforced
where transcript authority is read, not after a full reconstruction has already crossed the native
boundary. Persisting the visible slice also revealed a separate ownership rule: a projected window
must never stand in for the complete durable record.

## Next Horizon

The next Change Request remains an explicit Navigator selection. RS021 returns to its captured UX
priority, led by CR097. If complete earlier-history loading proves slow in practice, incremental
chapter loading is a separate Change Request rather than an unmeasured optimization folded into
this release.
