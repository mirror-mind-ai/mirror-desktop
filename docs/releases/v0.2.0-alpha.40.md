# v0.2.0-alpha.40 — Your Typing Survives a Changed Tree

**Date:** 2026-10-06

## Highlights

- Creating a Journey after Mirror changed underneath you now **keeps what you typed**: Desktop reloads the tree itself and asks for one more Confirm.
- A create that genuinely no longer fits says **which** thing changed — the id is taken, or the parent is gone — instead of a generic instruction to start over.
- The safety rule that caused the refusal is unchanged. Nothing is retried on your behalf, and nothing is merged automatically.

## Where We Started

Creating a Journey sometimes failed with:

> Journeys changed in Mirror. Reload the tree and try again.

The only recovery was to leave the form, reload the whole tree, and type the name, id, description and parent again.

The refusal itself was honest. Mirror protects its Journey tree by comparing a single fingerprint taken over *every* Journey — name, description, path, everything — against the fingerprint the Desktop's tree was loaded with. If they differ, Mirror does not guess; it refuses.

What made this frustrating is who usually changed that fingerprint: **you did.** Desktop loads the Journey tree when it starts and does not reload it on its own. So updating a Journey's path from Pi — which is what `mm-journey` does — changes the fingerprint, and the next Journey you create in Desktop is refused for a change that has nothing to do with it. The refusal was correct about the fingerprint and useless as an explanation.

## What Changed

### The form reloads the tree, instead of sending you out to do it

When Mirror refuses for this reason, Desktop now reloads the Journey tree in place and re-reads your create against it.

Only two things can actually make a create wrong: the id you chose is now taken, or the parent you chose no longer exists. Either one is named directly, and a parent that has vanished is reset to Root so you can choose again — Desktop does not pick one for you.

Anything else was never a conflict with your create, only a stale position in a tree that has moved. Your name, id, description and parent are kept, the position is recalculated, and the message tells you that one more Confirm will create it.

**Nothing happens on its own.** Desktop does not resubmit. The retry is you pressing Confirm, against current authority.

## Conscious Exclusions

**Mirror's safety rule is untouched.** The fingerprint and the comparison are exactly as they were. This release changes what happens *after* a refusal, not what gets refused.

**The tree is still not reloaded in the background.** Reloading it every time you open the create form would shrink the window without closing it, and would run a Mirror command on every open. The refusal is handled where it happens instead.

**Only creation is rebased.** The other Journey administration actions — move, delete, path changes — get the reloaded tree and a prompt to confirm again, not a rebase. They each name a Journey whose continued existence is the only thing to re-check, and the reloaded tree shows it.

**Renaming a Journey still does not work**, and this release does not fix it. *Save changes* in Edit Journey submits an operation no Mirror version accepts, so it has never succeeded. That is now diagnosed and recorded as a Mirror-side debt with its own Desktop fix pending; it is a different change from this one.

## What We Learned

**A correct refusal can still be a defect.** Mirror was right to refuse and the Desktop was right to ask. The failure was in the recovery: a rule designed to prevent one user from overwriting another's work was being triggered by a single person using two of their own tools, and answered with "start over".

**The diagnosis came from reading records, not from reproducing the bug.** This failure could not be reproduced on demand — it needs a Mirror change between two Desktop actions. It was resolved by reading the exact comparison in Mirror's code, the exact request the Desktop sends, and the live fingerprints, and by confirming that a refused attempt leaves nothing behind so a fresh retry is safe.

**Looking for one cause found another.** Tracing why a create was refused is what revealed that *Save changes* has never worked. Unrelated to this fix, unreported until now, and worth more than the fix itself.

## Next Horizon

The verification of this change needs the situation that caused it: change a Journey's path from Pi, then create a Journey in Desktop without reloading. Beyond that, the Edit Journey dialog needs to stop offering what it cannot complete, and a settlement that fails deep in its own machinery still does not always say which step refused it.
