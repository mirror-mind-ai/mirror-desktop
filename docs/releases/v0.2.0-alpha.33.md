# v0.2.0-alpha.33 — A Correction You Can Watch Arrive

**Date:** 2026-10-04

## Highlights

- A correction now reports `Correction reached the agent` the moment Pi hands it to the model, instead of reading `Correction queued` for the whole turn.
- Corrections are drawn inside the card of the run they corrected, where the work they act on is visible.
- `Correction applied` still means what it always meant: the correction has an exact Pi entry of its own.
- The status a correction reaches is no longer decided by four hand-written copies of one list.
- Carries everything from `v0.2.0-alpha.31` and `v0.2.0-alpha.32`, including the fix that stops Segment publication from truncating a Journey's durable turn ledger.

## Where We Started

Sending a correction while the agent was working produced a message that said `Correction queued`
and then said nothing more until the turn ended. For a long run that is most of the time you spend
waiting, and the one question it leaves unanswered is the only one that matters: did the agent get
it, or am I talking to myself?

The information existed. Pi emits a `queue_update` event each time it takes a steering message out
of its queue and hands it to the model. The Desktop handled no `queue_update` anywhere — the event
arrived and was discarded.

## What Changed

Delivery is read from **absence**. Pi's event carries the messages it still holds, not the one it
just delivered, so a correction is known to have been handed over when it stops appearing in that
list. Where the same text was sent twice, the copies Pi still holds are the most recent ones,
because Pi delivers in order.

That earns a new status, `delivered`, sitting between `accepted` and `applied`, and a new label:
`Correction reached the agent`, then `Correction applied` once the turn settles. Adding a status was
the honest option rather than letting the live signal satisfy `applied`. Pi mints entry identifiers
when it persists an entry, not while the turn is in flight, so the live signal cannot prove that a
correction became an entry. Weakening `applied` to a text match would have destroyed the evidence
the reload and recovery rules depend on.

The label deliberately does not say the agent *read* or *obeyed* the correction. A queue departure
proves the correction entered the model's input, and nothing more. Homologation vindicated that
restraint immediately: a correction reached the model and the model did not act on it as intended,
and the label had not lied.

Corrections also moved. They used to be drawn beside the prompt that opened the turn, which is the
one part of a long turn certain to have scrolled away by the time the correction matters. They are
now drawn in the run's own card, which already exists as the container for one run's work, and a run
with no narration of its own still draws a card when a correction belongs to it.

No durable write was added per event. The record is still settled once, when the turn finishes;
writing on every queue update would have reintroduced exactly the persistence traffic the previous
release was about.

## Conscious Exclusions

- No chronological placement of a correction inside a run. The trail mixes timestamped messages with
  untimed note subdivisions, so a spliced position would assert an ordering the data cannot support.
  "During" is carried in the header's words instead.
- No acknowledgement in the Composer. The run card already sits where the eye is, and transient
  notices have been rejected twice before.
- No full-session polling to confirm delivery, which would read an entire Pi session — measured at
  55 MB on a real Journey — on every correction.
- No change to Pi compaction, transcript authority, run authority or Journey identity.
- No change to how a Journey's working set is bounded.

## What We Learned

This release was finished, closed, and then reopened, because the closure was wrong.

The same list of statuses had been written by hand in four places. Two were inside the reconciler
and were updated; two were guards in the application that decide whether the reconciler runs at all,
and they were missed. A correction that reached `delivered` — the exact path this work exists to
produce — was therefore never reconciled and never acquired its entry evidence. The repair removed
the duplication rather than patching the two guards, because a fifth copy was only a matter of time,
and two further members of the same family were closed while the cause was in view.

The deeper lesson is about validation. The first homologation observed `Correction applied`
correctly, but only because the live transition was broken and the status had stalled one step
earlier, where the old guard happened to admit it. The fix that repaired the live transition made
`delivered` occur for the first time and silently voided that earlier observation, and nobody re-ran
the step. **A fix that changes which path the system takes invalidates every earlier observation of
the old path.** Those steps have to be re-run, not carried forward.

Both defects in this work shared one shape: correct domain logic, wrong wiring. Both passed
domain-level tests while the code deciding whether the domain function ran went untested.

## Next Horizon

A correction is still not recognisable after a reload: once the conversation is rebuilt from the Pi
session, a correction reads as an ordinary prompt and opens a run boundary of its own. That is CR097,
and it is the next selection in RS021.

One observation is recorded without a plan. A correction can *end* a turn rather than redirect it —
the agent takes the narrowing literally and stops. That is model behaviour, not something a transport
change in the Desktop can reach.

A separate Change Request, CR118, is in progress and **not** in this release. It makes a Journey
tolerate a Segment anchored to history its durable ledger can no longer see, which is a condition
stores carried on `v0.2.0-alpha.30` can hold until a compaction rebuilds their manifest.
