# v0.2.0-alpha.56 — A Refusal That Says Why, Without a Restart

**Date:** 2026-10-26

## Highlights

- **A provider refusal now names itself immediately**, under *Previous attempt was interrupted*, with no restart and no reopening.
- **An expired login, an exhausted quota and a timeout now read as three different things**, because the provider's own words are shown rather than a generic interruption.
- **A failure the provider did not explain is unchanged** — it keeps the notice it already had, rather than gaining an empty one.
- **Reading the reason can never cost you the turn.** If the transcript cannot be read, you lose the words and nothing else.

## Where We Started

Three turns in a row were refused and the application said nothing about why.

The Navigator's report was that the model was not receiving their messages. It was: every prompt
reached the provider, and the provider refused each one for a different reason — an expired
authentication session, an exhausted usage allowance, and four consecutive timeouts. Each reason was
recorded in the agent's own session file. None of them reached the screen, which showed only that the
previous attempt had been interrupted.

A change shipped ten days earlier exists to show exactly this. It was not broken. Fed the real
session file, cut at the instant of each failure, it produced all three messages exactly — so the
reading was correct and the fault lay elsewhere.

**The fault was in when the reading ran.** It had one caller: the path that restores a Conversation
when you open it. A refused turn marks itself as finalizing while it tidies up, and during that
window the restore path takes the Conversation already held in memory instead of re-reading the
session file. The event that would retrigger a restore happens inside that same window. So the reader
that worked was only ever reached by restarting the application — which is the one case its original
test covered.

## What Changed

The failure now reads the reason itself, through the same inspection and the same derivation the
restore path uses, immediately after the turn ends badly.

It is deliberately narrow:

- It runs **only** for a live turn that failed. A turn you cancelled is still reported as cancelled.
- It produces a result **only** when the provider actually left words. A crash or a silent death keeps
  the durable interruption notice it already had, rather than acquiring an empty one.
- It hands the words to the surface **only** while the same Journey, Conversation and generation are
  still in view, so a reason can never appear against the wrong conversation.
- It **cannot fail the turn**. On the restore path, evidence the derivation refuses marks the
  Conversation as inconsistent; after a failure that would be the wrong trade, so here an unreadable
  or untrustworthy transcript costs the words and nothing more.

Nothing else moved. The notice itself is the one built two releases ago; this release only gives it
something to say at the moment it is most needed.

## Conscious Exclusions

- **No retry is added, and no model or provider is changed.** The application reports what the provider said; acting on it stays with you.
- **An expired login or an exhausted quota still has to be resolved where it lives.** Naming the reason removes the guesswork, not the cause.
- **A failure with no recorded explanation gains nothing.** Rather than inventing a sentence, the existing notice stands.
- **Whether the live stream also carried the reason is still unproven.** The code path exists; there is no capture that would show whether it fired. The repair deliberately does not depend on the answer.

## What We Learned

**A correct reader is worth nothing at a moment it is never called.** The previous change was
verified by a fixture that reproduced the data shape, and the data shape was right. What no fixture
asked was whether anything calls the reader in the state the Navigator is actually in. That question
has now been written as a test that reconstructs the real sequence of events rather than the real
data.

**An instrument that cannot tell the before from the after proves nothing about either.** While
closing a separate change, two project surfaces turned out to carry wrong totals — one of them
introduced the day before. The check that should have caught them asserted a progress bar instead of
the counts, and the bar was mathematically unable to move for the change in question. Zero movement
from an instrument that cannot move is not a measurement.

**A repair observed once is not the same as a repair observed.** The settlement record introduced in
the last release was verified this week by two real recoveries in two different Journeys, against a
baseline of zero across every Journey on the machine. Its two remaining routes have still never run
in the field, and are recorded as unverified rather than assumed to work because a sibling does.

## Next Horizon

The check for this change is the next refusal: it must name itself on the spot, with the application
left open. A refusal that arrives and stays silent refutes it.

Separately, a turn froze for eleven minutes this week while the application finished saving it, and
during that time the whole application queued behind it — the conversation would not load, a second
conversation would not work either, and every button led into the same stalled queue. The cause is
understood and recorded: one step of the save waits on a helper process with no time limit while
holding a lock that most of the application needs. That is the next thing to fix, and it is the first
time its timeline could be read directly from a record rather than inferred from file timestamps.
