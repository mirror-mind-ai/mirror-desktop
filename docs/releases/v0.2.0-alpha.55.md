# v0.2.0-alpha.55 — A Repair That Leaves a Trace, and a Write That Cannot Drop Another

**Date:** 2026-10-19

## Highlights

- **A settlement completed through recovery now writes a record saying so,** in the same ledger and shape as an ordinary one, with its own phases and the route that repaired it.
- **A reader can tell *failed* from *failed and repaired*** without cross-referencing four separate artifacts.
- **All three recovery routes are covered, and the set is asserted at three** — an unnamed fourth would recreate the same silence for that one path with nothing failing.
- **A recovery pass that repairs nothing still writes nothing,** by construction rather than by a check. Idle recovery adds no write traffic.
- **Two agent-settings writes issued close together can no longer lose one of them.** The loss was silent: the second write succeeded, showed its success message, and left a valid file.

## Where We Started

Two changes, both about something that happened and left no trace.

The first was found in my own work. Diagnosing two turns that recovery had rescued took the turn
journal, a skips file, a provider session transcript and a file's modification time, because the
settlement ledger says nothing at all about a settlement that completed through recovery. The ledger
keeps the failure and nothing after it.

Grounding that this release also corrected an instrument. I had recorded two days earlier that a
ledger record carries no `runId`, so searching by it was invalid, and had been reading the file's
timestamp instead. The record does carry it — flattened at the top level rather than nested, and I
had read the key at the wrong level, so the lookup returned nothing for every record including the
control. The control had done its job by catching a broken instrument; my explanation of why it was
broken was the error. Read correctly it is decisive: all 232 records in this Journey's ledger carry a
`runId`, healthy turns are present, and both runs that recovery settled are absent.

The second change was a latent defect in how agent settings were saved. Every caller computed the
next settings from what its render had captured, then awaited the file write. Two writes issued
before the first landed therefore merged onto the same earlier value, and the second silently
overwrote the first — a Journey's model override vanishing with a success message on screen.

## What Changed

### A repaired settlement is now on the record

Each of the three recovery routes builds its own per-turn collector, times its steps, and emits a
record marked with the route that ran. The record is additive to the existing shape: an ordinary
settlement has no recovery marker at all, rather than an empty one, so a reader asking *was this a
repair?* gets no key instead of a value that might be a default.

The record leaves the recovery machinery as an event, and the application shell appends it through
the same path an ordinary settlement uses. That keeps the machinery from having to know about
storage — and it was the choice that could not be half-finished, because adding the event without
handling it does not compile. An emitted record nobody writes down would have been the same silence
with more code.

**A failed repair is deliberately not recorded.** Recovery runs when a Journey loads and while the
application is idle, so a repair that keeps failing would write a record on every pass — exactly the
write traffic two earlier releases exist to have removed. Recording only successes also makes *a
pass that repairs nothing writes nothing* true by construction: with no repaired turn there is no
collector, so there is nothing to write.

**A failure to write the record never fails the repair.** The repair is already on disk by then.

### An agent-settings write cannot drop another

The save now takes an *update* rather than a value. A caller cannot hand in a stale baseline because
it cannot hand in a baseline at all: one owner applies each update against its own baseline after the
queue grants it a turn. A failed write deliberately does not advance that baseline, so the next
update merges onto what is actually on disk, and one failure cannot poison every later write.

Reaching that required correcting the investigation that proposed it. It recorded that two menu
entries failed to close the menu before saving, and blamed that for making the race reachable. They
do close it — one layer up from where the investigation read. All four menu entries close the menu,
the close lands in the same commit that marks the save as in flight, and every one of the nine save
paths is already behind a control disabled while a write is running. **The race was not reachable
from the interface**, which made the planned repair a no-op and one half of it a setting that could
never be true.

So the repair became structural instead, and that crosses an exclusion the change request itself had
written. The exclusion was reasonable when the interface was believed to be the reachable cause; with
that refuted, what stood between the defect and the Navigator was an emergent property of nine
controls across four surfaces — not the kind of fact that stays true as code moves.

## Conscious Exclusions

- **The native recovery path does not write this record.** It runs in Rust while this ledger is written from the application side. It produces the work the other routes complete, so its repairs are represented by the route that finished them, and the record names which — specifically so the remaining path can be added later without ambiguity.
- **A failed repair writes nothing,** as described above. The capability exists and is tested; it stays unwired until there is a trigger that fires once rather than once per idle pass.
- **The agent-settings repair changes no behaviour you can see.** The race was unreachable before it, so nothing observable shifts. It removes a way for a future change to reintroduce a silent loss.
- **Neither change is field-verified yet.** The settlement record's check belongs to the next real recovery in production; the settings repair has no collectable check, because there was nothing observable to break.

## What We Learned

**Before believing a key is absent, print the record.** This is the second time in two days that
reading a key at the wrong nesting level produced a false conclusion, in opposite directions: once a
nested field read as flat, which reported that no settled record carried its execution evidence when
in fact every one of 643 did; once a flat field read as nested, which retired an instrument that
worked. One pattern, not two mistakes.

**The instrument's scope has to match the assertion's scope.** Checking a set of guard literals
against a whole source file passed, while three of those literals are matched against a *slice* of
it — and one had silently stopped matching.

**An ordering guard that compares two search results can stop guarding without failing.** A missing
literal reports as −1, which is less than every real position, so the comparison keeps passing
against nothing. Both positions are now asserted present before being compared. The rename that
exposed it was incidental; the missing presence assertion was the defect.

**A guard over a set must assert the size of the set.** The guard that was supposed to keep the model
menu inert during a save passed for a release while covering one element of five. The new guards
count their call sites, so a tenth caller cannot appear without the guard being read again.

**Check that a captured change request still describes the code.** Three in a row needed correcting
on contact: one named the wrong place for a collector, one named two recovery routes where there are
three, and one blamed a mistake that had not been made. A reading ages; the code moves under it.

## Next Horizon

The settlement record's field check is a search of the ledger by run identifier after the next real
recovery in production. It must appear there, settled, naming its route — where the two measured
before this release are absent. The same control that measured the defect confirms the repair, which
is the cleanest part of the arrangement.

What that will not establish is whether the phase *names* are the useful ones. Only reading a real
record for a real repair answers that.

Three earlier changes are still waiting on a single rare event: a turn freezing at *Finishing*. None
of them can be exercised until it happens again, which is why this release deliberately builds in a
different area rather than adding more work to that queue.
