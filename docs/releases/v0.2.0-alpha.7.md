# v0.2.0-alpha.7 — Four Concurrent Journey Turns

**Date:** 2026-09-14

## Highlights

- Runs up to four independent Journey turns concurrently through one exact Pi process per run.
- Preserves Journey, conversation, generation, run, turn, session, message, and registered-process authority under expanded concurrency.
- Keeps one reserved, running, or finalizing lease per Journey and counts finalization against the four-Journey admission bound until exact cleanup.
- Keeps ordinary occupancy quiet: there is no global process or concurrent-turn counter.
- Shows an actionable full-capacity notice only for the affected fifth Journey.
- Keeps the fifth Journey draft editable while disabling Send until capacity becomes available.
- Preserves owner-exact Steering, targeted cancellation, independent settlement, provider failure, and restart behavior.

## Where We Started

Mirror Desktop already supported independent Journey-keyed execution, but the production boundary admitted only two Journey leases at once. That conservative limit had proved process ownership, selective cancellation, settlement, and restart recovery, yet it interrupted natural cockpit use when several distinct Journeys needed to remain active together.

Increasing the number alone would not have been enough. Admission still needed to remain atomic, one Journey could not acquire multiple leases, finalizing work could not disappear from occupancy early, and every event or control had to retain its exact owner. Overflow also needed to remain recoverable without introducing a hidden prompt queue or turning the conversation surface into a process monitor.

## What Changed

The native Pi process registry now fixes the supported production horizon at exactly four admitted Journey leases. Reservation, duplicate-Journey rejection, and global capacity checking still happen atomically before process creation. The bounded shutdown path follows the same four-process horizon, attempts every captured child independently, and performs child control outside the registry lock.

The existing authority model remains intact at the higher capacity. Each Journey owns at most one reserved, running, or finalizing lease. Process exit terminalizes only the exact owner, first-terminal-wins prevents duplicate settlement, stale callbacks cannot mutate replacement runs, and finalizing leases continue to occupy admission until durable cleanup and fresh native reinspection complete. Steering writes to the owning Pi process and consumes no additional slot.

The desktop validates only governed inspection limits and derives admission for the selected Journey without exposing an aggregate process counter. Existing Journey-specific sidebar and conversation states remain the normal feedback. When four leases are occupied, a fifth Journey displays an English-only capacity notice, preserves an editable draft, and disables Send and Enter submission. Once exact cleanup frees capacity, Send becomes available for a deliberate retry. Native reservation remains the final atomic authority for races between inspection and submission.

Deterministic native tests cover four successful admissions, fifth-admission refusal, a five-way reservation race with exactly four winners, duplicate Journey rejection, finalizing occupancy, stale-target protection, selective cancellation, and bounded four-child shutdown. Frontend tests cover governed occupancy evidence, four-owner interleaving, silent ordinary occupancy, disabled overflow submission, and unchanged sibling state. Natural validation in the isolated development channel confirmed four simultaneous Journey turns and safe fifth-Journey recovery.

## Conscious Exclusions

- Concurrency above four is not planned or implied; it requires separately governed demonstrated need and new resource evidence.
- There is no user-facing capacity setting, environment override, global process counter, available-slot indicator, or process monitor.
- Overflow does not create a prompt queue, automatic retry, background send, placeholder, message, turn, generation, or process.
- One Journey still cannot run multiple concurrent turns in the same conversation.
- Steering remains text-only and reuses the exact active process; attachments, images, voice, follow-up queues, templates, skills, and cross-Journey targeting remain excluded.
- Apple Developer ID signing and notarization remain unavailable and are not claimed by updater signing.
- No stable-channel promotion, installation, publication, or unlimited concurrency is introduced by this release note.

## What We Learned

A useful concurrency boundary is not a visible process count. The Navigator needs trustworthy owner-specific states and clear guidance only when the bound affects an intended action. Keeping ordinary occupancy silent reduces cockpit noise, while disabling submission at known full capacity prevents a recoverable refusal from disturbing a draft or creating transient turn state.

The four-Journey horizon could safely extend the existing architecture because its invariants were already Journey-keyed. The important work was not a new scheduler: it was carrying atomic admission, exact cancellation, Steering reuse, finalization occupancy, stale-event quarantine, and bounded shutdown through a larger but still explicit envelope.

## Next Horizon

Observe four-Journey operation through the alpha channel. CV-008 can then continue with Persona Conversation Spaces, followed by explicitly governed multiple conversations per Journey and voice prompt composition. Any future concurrency growth should begin with measured need rather than treating four as an automatic step toward a larger number.
