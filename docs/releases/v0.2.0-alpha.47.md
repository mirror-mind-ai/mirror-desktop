# v0.2.0-alpha.47 — Nothing Fails Quietly

**Date:** 2026-10-12

## Highlights

- **A turn can no longer stop without saying so.** If the part of the app that owns a turn falls over, you now get told, and the turn is finished properly when its process has already exited.
- **A recovered answer lands in the right place.** When the app recovers an answer after a failure, it fills the space your question was already holding instead of adding a second copy beside it.
- **One silent failure mode is gone entirely.** A single internal fault used to make *every* turn after it end quietly, for as long as the app stayed open. That cannot happen now.
- **A new file may appear in your data folder.** `native-panics.jsonl` records an internal fault with the turn it belonged to. If it never appears, nothing went wrong — which is the normal case.
- **Nothing about a healthy turn changed, and that was measured, not assumed.**

## Where We Started

The previous release gave you two ways out of a turn that had already finished but still read as working. It deliberately did not explain *why* a finished process sometimes fails to hand its turn back. This release answers that, and the answer is embarrassing in a useful way.

Everything that finishes a turn runs on a thread the app starts and then forgets about. Every deliberate failure on that path is handled carefully — it finishes the turn, writes the record, tells the screen. **A crash on that path was handled by nothing at all.** The thread would unwind and vanish, and in a packaged app there is no console for it to complain to. The result was exactly the shape seen on 11 October: the process gone, the record frozen mid-turn, the lease still held, and the screen waiting forever for a signal that would never arrive.

Reading the code for that turned up a second fault sitting next to the first, and this one is worse. When a crash happens while the app is holding a particular internal lock, that lock stays broken for as long as the app runs. The code that finishes a turn would ask for the lock, be told it was broken, and treat that answer as *"somebody else already finished this turn"* — so it would do nothing, quietly. **One crash could therefore make every subsequent turn in that session end in silence.** Nobody had seen this, because the first failure already looked like a hang you restart past.

A third thing came out of the same investigation, from the record of the 11 October incident. The answer had been recovered and the screen was correct — but the stored conversation held four messages where there were two: your question twice, once empty and once answered. The screen was right the whole time, which is why it went unnoticed. The stored record was not.

## What Changed

### A thread that owns a turn cannot vanish without a trace

The turn-running body is now wrapped, so a crash comes back to a normal footing with everything still in reach. From there the app does what it does for every other failure: it checks whether the process has actually exited, and if it has, it finishes the turn properly — the answer is kept, the record advances, the screen is released.

If the process is still running, the app says so and **leaves it alone**. It does not kill it and does not pretend it died. That turn stays available for the release offer that shipped in the previous version, which becomes reachable the moment the process really exits.

And the fault itself is written down. `native-panics.jsonl` in your data folder records what happened and which turn it belonged to, because the probe into whether anything else would record it came back inconclusive — so the only honest answer was to write our own.

### A broken lock is reported instead of mistaken for success

The code that finishes a turn now distinguishes three things where it used to see two: *I finished this turn*, *someone else already did*, and *I could not tell*. The third case now speaks up and goes on to finish the turn anyway, because the parts that matter — writing the record, telling the screen — do not need that lock at all.

So a single crash can no longer quietly disable every turn that follows it.

### A recovered answer keeps the identity its place was held under

When you send a message, the app immediately reserves a spot for your question and the answer to come. When a turn had to be rebuilt from the agent's own session file, the rebuild could not tell that those reserved spots belonged to the same exchange — the information that links them is only written when a turn completes normally, and these turns had not. So it created a second pair, and anything that later combined the two sets kept both.

The app can now recognise that pairing for a turn whose work finished even though its bookkeeping did not, and it binds **both** sides — question and answer. One exchange, one identity, in the space that was already waiting for it. A recovered turn also now carries the information its own repair needs, which is what lets this work at all.

## Conscious Exclusions

- **We still do not know which of the two faults caused 11 October.** Both are real, both are fixed, and telling them apart needs it to happen again. The difference is that if it does, there will be a record instead of a silence.
- **One recovery path was left out on purpose.** The manual release that shipped last version cannot safely reconstruct an answer, because the reference point it would need has already been overwritten by the time you click it. Guessing there would risk attributing an older answer to the wrong turn, which is worse than the gap.
- **The conversation already stored twice stays as it is.** Your transcript reads correctly, so there is nothing to gain from editing the file, and editing your conversation records is not something this release does on its own.
- **`native-panics.jsonl` has nothing that reads it and never gets trimmed.** Each entry is bounded, so one fault cannot write without limit, but it is a file written for a future investigation rather than for you.
- **A turn that hangs while genuinely still working still has no exit.** Unchanged, and still a separate problem.

## What We Learned

**A probe that finds nothing has found nothing.** The first instinct was to search the system log for the crash. It held 163,154 lines from the app in the right window and not one crash among them — and that meant nothing at all, because nothing proved a crash would have reached that log in the first place. An absence with no control behind it is not evidence. That is the whole reason this release writes its own record.

**A guard is only as good as the fact it reads.** The code that finishes a turn was correct. It asked a question, got a misleading answer, and behaved perfectly on a false premise. This is the second release in a row where the bug was not a wrong decision but a right decision made on a stale fact.

**Finding the culprit was the wrong goal.** For the duplicated conversation we never did establish which piece of code combined the two sets of messages, and we stopped looking. Making the two sources agree on identity means any combination of them is correct, whoever does the combining. The fix is smaller than the investigation would have been.

**A guard caught the author twice, and both times it was working.** A rule shipped yesterday rejected this release's own first draft, and another rejected a test written for it. Both rejections were correct. A guard that only ever agrees with you is not a guard.

**Some of this cannot be proven in the field, and that is written down rather than rounded up.** Neither fix's success case can be staged on demand — provoking them means causing the crash. What the field did verify is the half that mattered most: that a healthy turn is untouched, and that the new pairing rule leaves existing conversation records byte-for-byte identical. That was checked against real conversations, not reconstructions.

**An unrecorded decision is a decision you did not think hard enough about.** A scoping choice made while writing the pairing rule went unwritten until after it shipped. Writing it down afterwards is what revealed the one case that could still go wrong, and it is why a field check happened at all.

## Next Horizon

Three things the same investigation turned up and did not fix. A turn that was asked but never answered still stores its question under the wrong identity, leaving its record pointing at messages that are not there. The place where two sets of messages get combined still trusts identity in a codebase where identity is precisely what gets lost when something fails. And the conversation list still reports some conversations as empty when they are not.

None of them lose anything. All of them are places where the record and the screen can still disagree.
