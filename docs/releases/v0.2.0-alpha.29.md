# v0.2.0-alpha.29 — Context Map and Agent’s Canvas

**Date:** 2026-10-02

## Highlights

- Renames the operational Context surface to Context Map, making its partial view of admitted context legible without exposing prompt text.
- Adds Agent’s Canvas, a Journey-owned `canvas.md` rendered by the app without imposing a genre, schema, manifest or persistence model on its contents.
- Lets the Navigator teach an agent how to draw and maintain its own canvas, then ask it to redraw through an explicit, unsent composer prefill.
- Re-reads a canvas only when the Navigator selects its tab or presses reload, preserving the last valid drawing rather than watching or polling the disk.
- Keeps a canvas honest about its limits: it reports no drawing, an unreadable drawing and a rendered drawing as different states.

## Where We Started

The Artifact tab had become a partial but useful account of what entered the agent’s context, yet its
name still described a file list rather than its actual role. A separate attempt to have a Journey
declare a workflow found a deeper version of the same problem: one Journey’s truthful state was
cash, positions and pending returns, but naming the surface Workflow made that state look wrong.

The agent could already work in a Journey’s files, but the Desktop offered no durable place for a
Journey to show what it considered important now. The product needed to host that drawing without
mistaking a format for understanding it.

## What Changed

**Context has an honest name.** The operational tab is now Context Map. It remains a bounded view
of material actually admitted to the active Conversation, without displaying envelope or prompt
text and without pretending that it is a complete project browser.

**A Journey can draw its own surface.** Agent’s Canvas reads a conventional `canvas.md` at the
Journey root and renders its Markdown. There is no manifest, source index, staleness verdict,
background discovery, watcher, polling loop or new persistence. The app knows the file’s state, not
its genre.

**Teaching and redrawing are distinct requests.** The empty state can prefill a request to teach the
agent to write its first drawing and short `canvas-instructions.md`. A drawn canvas can prefill a
redraw request. Neither button invokes the agent or sends a message: each moves the Navigator to
the visible Conversation composer with a draft ready to inspect and send.

**The agent’s drawing is derived and reloadable.** Selecting Agent’s Canvas or pressing its reload
control reads the file again. The last good drawing stays visible while a reload is in progress.
The reader rejects symlinks, unsupported types, oversized files and invalid UTF-8, and reports the
reason without reading standing instructions.

**The real runtime boundary is named.** Desktop invokes Pi from the Mirror root, so nothing at a
Journey root is loaded automatically. `canvas-instructions.md` is read when the redraw request
names it, or when the Navigator names it in conversation. The product does not ask the agent to
invent a pointer into a loader file that is not actually loaded.

## Conscious Exclusions

- No canvas content, instruction content, source list, freshness model or state lives in Desktop persistence.
- No filesystem watcher, polling, background scan, git-root discovery, manifest or directory search is introduced.
- No button sends a prompt or invokes an agent without the Navigator’s explicit review and submission.
- No link renderer, canvas editor, template, wizard, status vocabulary change, tag, push, publication, signing or notarization is included.

## What We Learned

The prompt was not the failing mechanism in the workflow experiment. The word was. The same agent,
with the same Journey and the same source material, dropped a stage table and obligation vocabulary
when the genre name disappeared, preserving the actual situation instead. Hosting less knowledge in
the app created a truer surface.

The validation also corrected a premise about standing instructions. Counting Journey-root loader
files does not establish that the Desktop runtime loads them. The live invocation directory does,
and it is the Mirror root. The redraw gesture is the live reader; the Navigator is responsible for
keeping the agent aware of when to use it.

## Next Horizon

The next Change Request remains an explicit Navigator selection. The captured RS021 order begins
with preserving a Correction’s recognisability after reload. Separate future work may decide whether
the Change Request vocabulary needs a status for work superseded by what it taught, and whether the
Canvas renderer should eventually support the document links that a freer agent will naturally want
to make.
