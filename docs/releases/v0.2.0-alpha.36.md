# v0.2.0-alpha.36 — A Failure That Says Its Own Name

**Date:** 2026-10-05

## Highlights

- A failed settlement records why it failed, and which step it was in — or which step it had just finished, when the failure fell between two of them.
- The two settlement steps that were never named now have names, so a fault in either is attributed instead of invisible.
- Two Journeys that failed to publish a chapter on **every single turn** can now publish.
- A Journey can write its first publication receipt instead of being refused for not already having one.
- Nothing changed for a Journey that was already healthy — verified Journey by Journey, not assumed.

## Where We Started

The previous release made a defect visible and then demonstrated the cost of not being able to read it. Twice in one day, naming why a settlement failed took a timing record, a handful of file timestamps, a census across twenty Journeys, and a read of the native source — to recover an error string the application already held in a variable and then discarded.

The reason it was so hard is that the measurement named phases, and both known failures happened *between* two of them. The record would say that the whole settlement failed while every phase inside it reported success, which is the least useful thing it could say.

The second problem was found by that same reading. A Journey publishes one chapter on an ordinary turn, which is not the whole conversation, so the publisher has to carry the historical message total forward from the previous receipt. Two Journeys had never managed to write one — because writing a receipt required every chapter the manifest declares to have a file, and a manifest legitimately names chapters from before publication existed. So the condition that would produce the first receipt could never be met, and every publication after that failed for the lack of it. Deterministically, on every turn, for days.

## What Changed

### A failure carries its reason

The settlement record now holds the error, together with the phase that failed — or, when the fault landed between two phases, the phase that had just completed. Both are worked out from the measurements recorded beside them rather than described separately, so a record cannot claim a failure that disagrees with its own phases.

The message is truncated if it is very long. That deliberately contradicts the rule the previous release introduced for measurements, which refuses an oversized diagnostic rather than trimming it, and the reason is that the two are different: a trimmed measurement reads as a true one, while a trimmed message is still the beginning of the right error and says plainly that it was cut.

### The two unnamed steps have names

Preparing the Mirror update and publishing the frontier to the surface were the only steps in settlement that the measurement did not cover, and one of them was where the previous release's defect threw. They are now named.

They are not timed in any meaningful sense, and the code says so where it is written: both are synchronous and cannot be slow, so recording a duration for them would invite a reader to treat them as costs. The names exist for attribution.

### A Journey can write its first receipt

When there is no previous receipt to carry a total forward from, the publisher now counts the chapters already on disk instead of refusing. Defaulting to zero was considered and rejected: it would have stuck, because the next compaction skips every already-published chapter and so is not treated as a full recount, which would have carried a wrong zero forward permanently.

The count skips anything it cannot read, stops at the same ceiling the recovery path already applies, and never fails — which matches what this artifact has always been, a deliberate lower bound rather than an authority.

### The receipt describes what was published

It is no longer withheld until every chapter the session contains is on disk. A receipt records a publication, and requiring the whole session to be published first conflated two different things: the chapter manifest describes where the agent's conversation was compacted, not which files exist. That conflation is precisely what made the condition unreachable.

## Conscious Exclusions

**No live run stands behind either change.** Both are covered by unit tests, by source guards for the parts that live inside native commands and cannot be unit-tested, and by replaying the real data read-only. No settlement has recorded a failure, and no publication has minted a receipt, on a build containing this.

The field test is unusually cheap and is a single turn: one Journey fails publication on every ordinary turn today, so the first turn there after this release must settle and leave a receipt. If it fails instead, the other half of this release will name the reason by itself.

**A chapter the manifest names but publication never covered is still not published.** Its messages stay out of the total, which is correct — they were never published — but the complete-history path still fails on the missing file for two Journeys, independently of the receipt. That is the next change in this area, not this one.

**A settlement that only succeeds through recovery still writes no record at all,** because the recovery path opens no measurement. The instrument reads first attempts only, so anyone counting records will undercount settlements. This is the largest remaining gap in it.

**Nothing yet distinguishes a recovered settlement from slow work on the surface.** It should, and it is deliberately not built here: two known defects were still changing the failure rate while this was written, so a surface designed against today's failures would have been designed against a moving target.

## What We Learned

**A diagnostic that cannot name a cause is an expense, not an instrument.** The measurement introduced two releases ago was correct and well-tested, and it still cost two full investigations, because it recorded where time went and not what went wrong. The fix was one field.

**Deleting a planned slice can be the most useful part of the work.** This release was supposed to time two steps. Reading the code showed both were synchronous and pure, so timing them would have produced numbers that mean nothing and would have been read as costs for years. Naming them was what was actually needed, and the comment at each site now says which of the two it is doing.

**Two defects can hold each other up, and fixing either alone changes nothing.** The refusal and the unreachable condition had to move together: repairing only the refusal would have run an expensive fallback on every turn forever, and repairing only the condition would have left the already-stuck Journeys stuck.

**A guard that fails for the wrong reason gets relaxed rather than fixed.** One source assertion here failed because another test used the old error message as sample data. Narrowing it to the production source was the correct response; weakening the assertion would have been the easy one.

## Next Horizon

Read the two field results, both available on the first turn in the affected Journey. Then publish the chapters a manifest declares but publication never covered, which is what still keeps complete history unreadable for two Journeys. After that, the empty chapter file that a closing chapter wrote over its own content, and the question this release deliberately left open: whether a settlement that only survives because recovery caught it should look any different from one that simply took a while.
