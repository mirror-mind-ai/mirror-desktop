# v0.1.1-test.1 — Private Update Channel Rehearsal

**Date:** 2026-09-08

## Highlights

- Publishes the first private test release artifact for the Mirror Desktop updater channel.
- Uses the discreet header version chip as the user-visible update surface.
- Shows the current app version when current and composes it with a short `Update` action when a newer version exists.
- Keeps the update popover in English and on an opaque, readable surface.
- Connects release candidate provenance to versioned release notes under the private update endpoint.

## Where We Started

The self-update mechanism had already been proven in a private clickable rehearsal, but that rehearsal used temporary version hops and transient local signing keys. The user-facing update surface also needed one more pass: the application is currently English-only, so the chip and update popover needed to match the rest of the product language, and the version should remain visible even when no update is pending.

The release-note path was also missing from the Desktop release ritual. Mirror Core already treats release notes as part of the release boundary, not as an afterthought. Mirror Desktop needed the same shape before the updater channel could become a reliable private distribution path.

## What Changed

The header update surface is now a persistent version chip. When the app is current, it reads like `Mirror Desktop 0.1.1-test.1`. When the updater sees a newer signed release, the same chip becomes `Mirror Desktop 0.1.1-test.1 • Update`. Clicking it opens a compact English popover with the available version, current version, preservation boundary, and actions for later, details, and update.

The release process now has Mirror Core-style release notes in `docs/releases/`, a generator and validator in `scripts/release_notes.mjs`, and release candidate provenance that points to the expected release notes URL. This private test release is built against the private HTTPS endpoint at `updates.mirrormind.sh` with updater artifacts enabled.

## Conscious Exclusions

- This is a private test release, not a public production release.
- No Git tag, GitHub Release, stable promotion, or public announcement is created by this note.
- No macOS notarization claim is made.
- The private updater key used for this test channel is not yet the final production key custody process.
- The updater still replaces only application bytes. Mirror homes, `memory.db`, identity, credentials, Journey content, conversations, app data, and Nautilus Harness state remain outside the mutation boundary.

## What We Learned

A release channel is a trust surface and a reading surface at the same time. The artifact can be signed and still feel rough if the app does not tell the user where they are. The version chip solves that by making version presence ordinary and update action exceptional.

The release note completes the same gesture in documentation. It tells the updater what changed, but it also tells the maintainer what was consciously not claimed.

## Next Horizon

After this private release rehearsal is accepted, the next boundary is release-channel hardening: decide key custody, artifact retention, manifest generation, notarization policy, and the exact route from private test release to an official alpha or production release.
