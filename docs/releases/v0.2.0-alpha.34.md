# v0.2.0-alpha.34 — A Finish You Can See Through

**Date:** 2026-10-04

## Highlights

- A Segment whose anchor no longer exists in the durable ledger no longer makes settlement throw; the part of history the ledger cannot see is treated as already published.
- A closed chapter supplied empty no longer overwrites the chapter file that still holds its history.
- One settlement fault now produces one notice, rather than itself and a second count of itself.
- `Finishing` can name the step it is in after a wait has become visible.
- Each settled turn records how long its saving phases took, once, so the next reduction can target evidence instead of intuition.

## Where We Started

A production Journey on `alpha.30` held a Segment manifest that still pointed at chapter anchors its durable turn ledger had lost. The old partition assumed every anchor could be resolved in that ledger. It could not: the guard threw deterministically, and the settlement surface announced the same fault twice.

The immediate symptom was repaired in the store before the upgrade, but that was deliberately a symptom repair. The `alpha.31` publication change stopped the overwrite that had removed the ledger history, and `alpha.33` carried the correction work that followed it; neither made the partition tolerant if an older store still carried the shape.

At the same time, `Finishing` often looked identical to a hang. It was usually not stranded. Across 569 timed production settlements, 17% ran longer than two minutes, but nothing said which part of finalization took the time. Between Journeys the wait tracked conversation size; inside one Journey it swung from seconds to thirty minutes with no relationship to session size, turn size, or work duration. Four plausible causes were tested against what existed and eliminated. Choosing a fifth by intuition would have been theatre.

## What Changed

### A chapter can be anchored only to history the ledger can see

The partition now recognizes three anchor states: resolved, unanchored, and unresolvable. An unresolvable anchor is a **cut**, wherever it appears. Everything before that cut is treated as history already published; the current Segment is always retained. Starts are resolved from the right, so an unanchored Segment inherits the next Segment's start rather than making the remaining partition non-monotonic.

This is deliberately a tolerance rule, not a reconstruction. The renderer does not hold Pi entry positions at settlement, so it cannot truthfully re-anchor a ledger record whose history is absent. The native manifest refresh remains the authority that can rebuild those anchors when the source session is available.

Closed chapter files are the surviving historical record. When a closed Segment is supplied empty because the ledger can no longer see that chapter, publication now skips it rather than asking an empty projection to replace a file holding real history. The receipt counts only Segments it wrote or verified, so a bundle that skips closed chapters cannot erase their message count from the catalog.

And one settlement fault yields one notice. The diagnostics projection drops the exact debt whose text is already the Journey-level failure; it does not pretend one thrown error is two independent problems.

### Finishing is observable before it is made faster

Each settlement now accumulates elapsed time for its named phases in memory: checking the Journey, saving the durable conversation, loading or refreshing chapters, publishing them, queueing and delivering to Mirror, recording the turn, and confirming delivery. It writes one completed record per settled turn to a bounded per-Journey diagnostics file.

The record deliberately does **not** live in the turn journal. The journal has a strict native schema, and its phase, revision and receipt fields govern recovery. A diagnostic must not be coupled to the structure that keeps recovery safe. Nor does it write per phase: CR116 taught that persistence traffic on finalization is itself dangerous. A diagnostic write that fails is a warning, never a failed turn.

After three seconds, `Finishing` names its current step in words such as `publishing chapters` or `sending to Mirror`. A fast turn looks exactly as it did before.

The first Dev reading is a beginning, not a conclusion. Its tiny Journey settled in 2.026 seconds, of which Mirror delivery used 1.514 seconds. That is an interesting signal because delivery does not scale with session or projection size; it is still one fast turn and cannot explain the production tail. The release creates the data needed to answer that question honestly.

## Conscious Exclusions

- No attempt to reconstruct a missing Segment anchor from a renderer that does not possess the needed Pi entry positions.
- No rule to publish only the just-closed and current Segments on compaction. That is a separate design change, recommended as its own Change Request.
- No lowering of the CR116 120-second bound. It stops a wait that will never end; it was never meant to police ordinary slowness, and it is per operation rather than per turn.
- No claim that `Finishing` is shorter. This release makes it legible and measurable first.
- No unblocking of sending during `Finishing`. The answer is already committed to Pi before finalization begins, so it may be safe, but ordering and run authority deserve a separate decision informed by production phase data.
- No change to the turn journal schema, Pi session authority, compaction semantics, correction delivery, or Journey identity.

## What We Learned

A field symptom can be real and still be attached to the wrong mechanism. The first CR118 capture read the Dev store and framed the report as a regression from correction work in flight. Production was the actual site, and the real mechanism was the opposite: the ledger had lost history that the manifest still remembered. The provenance correction mattered because it changed the fix from “re-anchor at the start” to “cut where the ledger cannot see.”

The same discipline governed `Finishing`. The broad data produced a strong correlation with session size; inside the affected Journey, that correlation vanished. The code then disproved the most tempting story — settlement does not reread the Pi session — and the compaction hypothesis had no support in the available windows. Measurement is not delay when it rules out a convincing wrong answer.

And a guard needs a visible failure mode. `pgrep -f` returned “not running” in this environment even for processes `ps` listed plainly. Several observations were corrected once that was discovered. The durable lesson is simple: prefer a check whose failure is visible over a convenient check whose absence looks like proof.

## Next Horizon

The new timing file needs ordinary production use. Once it has a meaningful sample, the per-phase reading can distinguish the size-driven floor from the episodic long tail and justify a reduction Change Request. The leading candidate from the first Dev record is Mirror delivery; it is not a conclusion.

A separate decision remains: whether a Navigator should be allowed to send during `Finishing`. That may remove the felt cost even before the work is shortened, but it must preserve turn ordering and exact run authority.

CR097 remains the next selected product continuation: a correction should still be recognizable after the conversation is rebuilt from the Pi session.
