# v0.2.0-alpha.37 — What Is Already There Keeps Its Place

**Date:** 2026-10-05

## Highlights

- A chapter that closes with nothing to say no longer overwrites the file holding its history.
- An already-damaged chapter file is repaired at the next compaction rather than defended forever.
- Three Journeys that failed the publication half of **every** compaction can publish again.
- The Conversation no longer slides upward when a turn settles, so the answer you were reading stays where your eyes are.
- Replayed Journey by Journey against real data: all fourteen now complete a compaction, and nine chapters that were failing now stand.

## Where We Started

The previous release left one defect on the board and a prediction about it. A chapter had closed with an empty slice of history and written that emptiness over its own file: 606 KB of conversation replaced by a file claiming thirteen turns and containing none. The plan said repairing the write order would heal it and let the compaction through.

Half of that was right, and finding out which half is most of this release.

The reading that caused the trouble is a reading nothing else in the system takes: when a compaction publishes, it re-derives a projection for every closed chapter and compares it byte for byte against the file already on disk, failing the whole publication on any difference. That compare looks like an immutability guarantee. It is not one, because only one side of it is immutable.

## What Changed

### A closing chapter stops erasing its own file

The rule that lets a chapter replace its own file is there for a good reason: a chapter written while it was still open holds less than the chapter that eventually closes, so the closing write has to land. But that permission was being granted before the question of whether there was anything to write, so the one chapter allowed to overwrite itself was also the one chapter exempt from the rule that an empty projection must defer to the file still holding the history.

Emptiness is now decided first, and the permission only decides what to do with content.

### A file that holds nothing yields to the projection that does

Where the previous release taught the publisher to defer to a file when the projection was empty, this one teaches it the converse: when the *file* is empty and the projection has messages, the file is the damage and the history is what replaces it.

A file that cannot be read at all is deliberately not treated as empty. That is a different kind of damage, and overwriting it without understanding it would be worse than leaving it alone and saying so.

### A published chapter is its own authority

This is the correction, and it matters more than the fix it corrects.

Replaying the plan against real data showed the empty chapter healed and the compaction still failing — one chapter later, on a file that was perfectly intact. It had been written while that chapter was still open, and the compaction that closed it moved the boundary by one turn and never came back to rewrite it, because the publication had already aborted earlier in the same pass.

And it was not one chapter. Of the fourteen closed chapters a compaction would supply with content, **eleven differed from their files**, across three Journeys, in both directions — some files holding more than the conversation now reaches back to, one holding less.

That is the clearest possible sign that the comparison was not measuring what it claimed. The file is immutable. The projection it was being compared against is re-derived every time from a conversation whose loaded window and turn boundaries change by design — bounded three releases ago, made tolerant of unreachable anchors two releases ago, corrected again in the last one. Byte equality between them was never something the system maintained, so it failed for reasons that had nothing to do with any chapter being wrong.

The publisher now defers to the published file. It still reads it, for one reason: to notice it holds nothing, and heal it.

The guarantee that was supposedly being protected is unaffected, because it was never living there. A published chapter's bytes are verified against the completion receipt **when the chapter is read**, which is where corruption would actually matter, and that check is untouched.

### The Conversation stops sliding away from what you were reading

Submit a turn, read the answer as it arrives, and the moment it finishes the surface slides upward on its own — sometimes as far as earlier turns.

The cause is a single transition. The instant a run ends, the turn before it stops being the most recent completed one, and a turn that is no longer the most recent collapses its entire trail of actions and surfaces into one summary line. That happens directly above the reader, in one frame, and the window Mirror Desktop draws in does not implement the browser mechanism that keeps visible content still when layout above it changes. Nothing had scrolled, so the scroll position stayed exactly where it was while the content underneath it moved.

The surface now remembers which message you are looking at and where it sits on your screen, and puts it back after the layout changes — before anything is drawn, so the displacement is never shown and then undone.

A reader already at the end of the conversation was never affected, and it is worth saying why, because it is the reason this fix is complete rather than half of one: when content above shrinks, the scroll position has nowhere to go but down by the same amount, and the two cancel out exactly. The problem needs a scroll position free to stay still, which only happens once you have scrolled away.

## Conscious Exclusions

**No compaction has run on this build.** A compaction cannot be scheduled — it happens when the agent's context fills. So the publication changes rest on unit tests, on source assertions for the parts that live inside native commands, and on replaying the real store read-only, where all fourteen Journeys now complete and nine previously failing chapters stand. The observable event is the damaged chapter returning to its 606 KB of conversation at the next compaction in this Journey.

**The scroll fix has no field verification either,** and cannot: scroll position is not durable, so there is nothing to replay. It rests on fourteen tests, six of which assert where the correction is wired rather than what it computes, because a correct rule in the wrong place is this codebase's recurring failure.

**A turn still loses its detail the instant it stops being the newest.** Keeping your place makes that harmless to read around, but whether a finished turn should collapse that eagerly is a question about what the surface says rather than where it rests, and it is deliberately left open.

**Two chapters sharing a single anchor is still the upstream cause** of a chapter being handed an empty slice in the first place. Six generations already carry that shape. Three successive releases have made it harmless rather than absent.

**The receipt can no longer recount its own total during a compaction.** Deferring to a published file means a compaction is no longer treated as a full recount, so the historical total stays a figure carried forward. In practice it already was, for weeks. But the path that could have corrected a drifted total is now unreachable, and the honest answer is the one the architecture document already recommends: stop storing counts that are derived and count the files.

## What We Learned

**A plan that predicts an outcome should be replayed before it is believed.** This one predicted that healing the damaged file would let the compaction through. The fix was right, the prediction was wrong, and the only reason that was caught before shipping is that the prediction was checked against real data instead of against the reasoning that produced it.

**Verifying immutable data against a derivation that moves is not a guarantee, it is a trap.** It reads like safety. It had been failing three Journeys on every compaction for days, in both directions, and the direction is the giveaway: a check that fails when the file has *more* than the derivation is not protecting the file.

**The tempting smaller fix was the wrong one.** The same event already publishes a narrower bundle when the Navigator triggers a compaction by hand, and matching that in the automatic path would have been less code and reused a tested function. It was rejected because the damaged chapter would then never be supplied again, and the repair this release exists for would have become permanently unreachable. The failure would have disappeared and the damage would have stayed.

**Scoping a fix correctly can make it complete.** The scroll correction protects only a reader who has scrolled away from the end. That looked like half an answer until the arithmetic showed the other case is already stable for a reason that has nothing to do with this code. Knowing why a case does not need fixing is worth as much as fixing it.

## Correction (2026-10-05, after this release was published)

Two claims above are wrong, and the error was mine rather than the product's.

"Three Journeys that failed the publication half of **every** compaction can publish again", and the
figure of eleven differing chapters, were measured by replaying the publisher against the stored
conversation ledger. The publisher is actually handed the loaded surface, which is bounded to the
current chapter. On an ordinary compaction every closed chapter except the one that just closed
arrives empty and is skipped, so the comparison this release removed was never reached. A compaction
ran on the previous build, still carrying that comparison, and completed.

What stands: the comparison was unsound — it checked an immutable file against a projection re-derived
from a window that moves — and it is reachable when a compaction settles while complete history is
loaded. There is no evidence it ever failed a real publication. The chapter that overwrote its own
history with an empty file is unaffected: that damage is real, it fired, and the first half of this
release is what repairs it.

So this release is better described as removing an unsound check and repairing one damaged chapter,
not as unblocking three Journeys.

## Next Horizon

Watch for the damaged chapter's history returning at the next compaction here — the one event that demonstrates both publication changes at once. Then the chapters a manifest names that publication never covered, which is what still keeps complete history unreadable for two Journeys. After that, the question three releases have now deferred: whether counts that are derived should be stored at all, or computed from the files that hold the answer.
