# v0.2.0-alpha.21 — Journey Binding Defence

**Date:** 2026-09-26

## Highlights

- Restores the Journey binding of a Conversation Mirror Desktop provisioned, when something outside the Desktop has moved it.
- Delivers once more after the repair, so a broken conversation heals without any Navigator action.
- Stops retrying rejections that repeating can never resolve, and surfaces them immediately instead of after a second failure.
- Names the actual divergence in the synchronization notice, above the raw reason code.
- Records each performed repair as bounded durable evidence, naming the Journey it was found under and the Journey restored.
- Never moves a Conversation the Desktop did not create.
- Opens a register for Mirror core defects the Desktop discovers but cannot correct.

## Where We Started

A Conversation ran normally for two turns and then stopped synchronizing. The
third turn was rejected with `journey_mismatch`, and every retry after it was
rejected the same way, for forty-four minutes, while the interface reported
only a generic partial convergence.

The Desktop was not at fault in what it asserted. Its durable thread authority
named the right Journey on every attempt. Mirror held a different one: the
`journey` column of that Conversation had been rewritten underneath it, and the
append contract correctly refused a request that disagreed with the record.

The cost was larger than a stuck outbox. Two turns had already been accepted
before the rewrite, so one Journey's record silently lost them while another
silently gained them. Nothing anywhere had logged the change. It was
reconstructible only because three unrelated rows happened to carry an
`updated_at`.

## What Changed

**Rejections are now classified by whether repeating them can change anything.**
Mirror's append contract refuses a request for bounded, named reasons. Some of
those are facts about the durable record — a mismatched Journey, a conflicting
message identity, a Conversation that no longer exists. No number of retries
will alter them. Those now stop the retry loop and ask for attention on first
sight, rather than waiting for the second failure the patience gate was built
for. That gate still applies to everything that might genuinely self-repair.

**A drifted binding is repaired and the delivery is retried exactly once.** The
Desktop proves ownership first, from the same durable thread authority the
outbox already validates against: the Conversation must be the one this thread
provisioned. Only then does it restore the Journey column, and only that
column. It has no authoritative value for anything else and does not invent
one. The single-attempt bound is enforced by the type system rather than by
convention.

**The notice says what diverged.** A bounded contract rejection now carries a
sentence naming the cause above the reason code, in both synchronization
notices, with a contrast rule for light and dark themes.

**Each repair leaves provenance.** The first version of this defence healed
silently and recorded nothing, which meant that proving it had acted at all
required cross-referencing unrelated tables. That is precisely the property
that let the original incident hide, and the Desktop should not reproduce what
it is defending against. A performed repair now appends a bounded record naming
both Journeys, written only after Mirror confirms the restore so the evidence
can never claim a write that did not land, and structurally unable to fail the
repair it is recording.

**Mirror core debts have a home.** The Desktop runs on a Mirror core it does not
own, and findings like this one had nowhere to live: too specific for a
conversation, too foreign for a Desktop change request. They were being absorbed
into defensive code whose real cause became invisible. RS022 now registers them
with evidence and provenance, so the debt stays visible and attributable.

## Conscious Exclusions

- No Mirror core change. The defect that rewrites the binding is registered as RS022 / CR094 and remains uncorrected; this release contains the defence, not the fix.
- No Navigator-visible notice for a repair that succeeded. A single repair is ordinary self-healing, and alpha.13 settled that self-repairing state must not become visible flicker. The evidence exists and is readable; deciding how to surface repeated repair needs a threshold design and belongs with whoever builds that notice.
- No recreation of a Conversation Mirror no longer holds. That is indistinguishable from an intentional deletion, and the decision belongs to the Navigator.
- No repair of a Conversation the Desktop did not provision, ever.
- No durable suppression of further attempts after a terminal rejection. With the repair in place the loop that motivated it no longer occurs; suppression would need per-item durable state and a rule for clearing it.
- No change to Pi JSONL, the turn journal, the outbox schema, cancellation semantics or the native lease lifecycle.

## What We Learned

The homologation taught more than the implementation did. A passing result was
not proof: a Mirror Mode activation resolving the same Journey would have
restored the column too, so the test could have succeeded for the wrong reason.
Excluding that required checking that no session row had been touched, since
every Mirror-side writer updates one in the same call.

That exercise is what exposed the missing provenance, and the fix for it closed
the loop in an unexpected direction — the record now attributes the write
directly, so it retroactively strengthened the evidence for the defence it was
built on top of. Observability is not only for production incidents; it is what
makes a test conclusive.

The second lesson is about ordering. The repair mechanism was proven against
Mirror's real append contract in a throwaway database before the assembled
route ran anywhere, which meant the app-level homologation had only one
unknown left to resolve instead of several.

## Next Horizon

RS022 / CR094 holds the real correction, blocked until Mirror core becomes
available for modification. Until then the register accumulates what the
Desktop learns about the runtime beneath it. If the repair records show the
drift becoming routine rather than exceptional, the decision to keep repairs
silent should be reopened with that evidence in hand. CR092 proposes moving the
recenter control out of the header into a floating affordance, and the
remaining RS021 pre-beta work continues toward a beta-ready daily application.
