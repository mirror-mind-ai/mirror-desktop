# v0.2.0-alpha.32 — A Stranded Journey Comes Back

**Date:** 2026-10-03

## Highlights

- Bounds every per-Journey persistence and finalization operation, so one that never settles fails instead of stranding the Journey.
- Keeps the post-terminal repair route reachable exactly when a Journey is stranded in finishing.
- Reports a given-up step truthfully, naming what survived it rather than leaving `Finishing` on screen forever.
- Refuses repair on native Pi execution rather than on a renderer flag a stopped settlement leaves set.
- Preserves the quiet idle recovery behavior introduced in `v0.2.0-alpha.30` under a regression test.

## Where We Started

A Journey entered `Finishing` after its turn had completed and stayed there. Cancelling did nothing,
sending was blocked, and the repair control never appeared. The Journey was unusable for the rest of
the application's life, and the only escape was to quit and reopen.

The agent's work was never at risk. The answer had already been committed to the Pi session, with
its exact entry coordinates present in the session file. What failed was the Desktop's post-turn
bookkeeping, and that failure had no in-session exit.

Read-only inspection found the turn's journal record at `terminal_durable` with a `completed`
outcome, while the durable projection had last been written two minutes earlier, at the start of the
turn. Post-turn persistence had therefore never written anything. Disk space, the delivery outbox
and child processes were all excluded as causes.

## What Changed

Three per-Journey serialization layers were involved, and none of them was bounded. Both queues
already recovered from a predecessor that *rejected* — that was deliberate design. Neither recovered
from a predecessor that never settled. Worse, the finalization queue is shared by finalization,
interruption and delivery convergence, so a stalled finalization parked the very recovery routine
that was supposed to release it. Correcting only the repair route's guard would have changed nothing:
repair would have hung rather than being refused.

So the bound is the load-bearing change. One seam, used by both queues, stops the wait rather than
the work. When it expires the caller fails with a reason naming the phase that stopped, the queue
advances, and the abandoned operation keeps running detached with its late outcome absorbed. The
ceiling is deliberately generous at 120 seconds, because a real Journey legitimately writes
multi-megabyte projections and inspects a session measured at 55 MB. A bound that fired on ordinary
slowness would be a worse defect than the strand it replaces, and a false positive degrades only to
settling later through recovery.

Abandoning a pending write is safe on checked ground rather than by assumption. Journal transitions
already carry native revision and phase expectations, and durable projection writes are already
staged with the previous file preserved on failure, so a revived operation can only lose — it cannot
regress a record.

The repair route now refuses on native occupancy, which knows whether Pi is genuinely executing,
instead of on the renderer's active-or-finalizing flag that a stopped settlement leaves set forever.
The flag itself is unchanged and still guards admission and cleanup, where refusing during
finalization is correct.

The stranded surface needed no new runtime state. A retained finalizing lease together with a
settlement error already renders the repair notice and its control; it never appeared only because
the operation hung instead of rejecting. Bounding alone restores it. The single missing piece was
honest wording, so a given-up step now says that it stopped responding, that the answer is preserved
in the Pi session, and that repairing synchronization completes the turn from that evidence.

## Conscious Exclusions

- No new durable artifact for an abandoned operation: the journal record left at its unfinished phase is already that fact.
- No parallel runtime state for stalled finalization, which would have duplicated a working surface.
- No change to Pi compaction, transcript authority, run authority or Journey identity.
- No repair or rewriting of pre-existing inert journal records, and no production data mutation.
- No tightening of the bound without measurements from large real Journeys.

## What We Learned

A queue that survives failure is not the same as a queue that survives silence, and the difference
is invisible until something hangs. Both coordinators had been written carefully against rejection
and were defenceless against a promise that simply never settled.

The second lesson is about guards. A repair routine gated on the condition it exists to repair will
always decline at the one moment it is needed. The authority for "is work really happening" belonged
to the native registry all along, not to a renderer flag that depends on the very code path that
broke.

Reading the code also prevented two unnecessary builds: the visible surface and the durable record
both already existed, and only the timing and the wording were missing.

## Next Horizon

The exact operation that never returned remains unestablished, and no cause is claimed. The incident
is not reproducible on demand, so the stranded path is proven by test rather than by reproducing it.
Phase-level timing or an abandonment diagnostic may follow if an operational need appears.
