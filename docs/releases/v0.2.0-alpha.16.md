# v0.2.0-alpha.16 — Deterministic Release Deployment

**Date:** 2026-09-22

## Highlights

- Publication destination is derived from the application's own updater endpoint instead of a separate constant in the publisher, so the release can only land where installed applications actually look.
- A publication aimed at a destination that diverges from the application endpoint now fails closed instead of reporting success.
- Post-publication verification polls the exact URLs an installed application reads and blocks the route unless each one serves the released version with a signature.
- Retained versions and manifest paths are derived from Git tags rather than typed by hand for each release.
- Release evidence is generated from the data the route actually used, ending hand-composed documents.
- Publishing a release is one instruction with a single confirmation after preparation, taken over real artifacts and the authored release note.

## Where We Started

Alpha.15 shipped correct software to the wrong address. The endpoint installed
applications poll lives in the channel updater configuration; the publisher
carried its own base URL constant, and the two disagreed. The publication
reported success, and verification across six manifest paths came back clean —
none of those paths was one any installed application reads. The defect
surfaced only when the Navigator opened Alpha.14 and saw no update indicator.

Underneath that was a process shape: every step was a hand-typed command
interrupted by its own authorization request, while the checks that would catch
a real defect depended on the operator choosing to perform them. The Navigator
was interrupted often for permission and served poorly by verification.

## What Changed

The publisher no longer holds an independent notion of where a release goes. It
reads the first endpoint from the channel updater configuration and strips the
polled manifest suffix, so the destination and the application agree by
construction. An explicitly requested destination that diverges is refused.

Preparation and publication became one resumable route. Preparation runs
preflight, the full test and build gates, the signed channel build and candidate
inspection without interruption, then presents one confirmation carrying the
authored release title, the full release-note text, the candidate revision, real
artifact checksums, the derived destination and the exact manifest paths.
Everything after that confirmation runs to completion: push, tag, prerelease,
endpoint publication, verification and evidence.

Verification became a gate rather than a courtesy. The route fetches every
target and retained-version URL an installed application would poll and refuses
to finish unless each serves the released version with a non-empty signature.

## Conscious Exclusions

- No user-facing product behavior changed in this release.
- The route is proven end to end only by a real release; its outer steps are verified by use, not by test doubles.
- Verification proves the manifest an installed application would read, not that a running application downloaded and applied the update.
- No notarization, no public announcement, and no promotion to stable or production.
- No Mirror data, Journey data or application data is touched by the route.

## What We Learned

A verification that the operator composes by hand verifies the operator's
assumption, not the system. Six clean checks proved only that the artifacts
reached the place we believed in, and belief was the broken part. A check earns
its keep when it is derived from the same source of truth the product uses, and
when failing it stops the route.

The interruptions were also aimed at the wrong thing. Asking permission six
times did not make the release safer; it made the operator the integration
point. Authority belongs to the Navigator once, over materialized facts;
mechanics belong to a script that refuses to continue when something is wrong.

## Next Horizon

Exercise the route on a real publication and confirm an installed application
updates from it. After that, the remaining manual step is installed-app update
validation, and the natural follow-on is making a second channel select its
configuration explicitly rather than binding to the alpha one.
