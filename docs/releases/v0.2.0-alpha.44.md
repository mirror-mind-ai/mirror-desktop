# v0.2.0-alpha.44 — Two Conversations at Once

**Date:** 2026-10-10

## Highlights

- **Two conversations in one Journey can run at the same time.** Up to three, with the fourth refused by name rather than by a generic busy state.
- **The list says which conversations are working.** A mark beside the title, per conversation, including when the working one is hidden or folded behind *Show N more*.
- **A refusal explains itself.** Every reason Send can be unavailable now has one sentence, written in one place, and the one that names a Journey's occupied slots says *who* is holding them.

## Where We Started

The previous release made ownership legible and said plainly that concurrency was not admitted: *"Starting a turn while a sibling conversation is working is still refused."* This release admits it, and the route there was not the one that was planned.

**One run per Journey was built in at four separate layers.** The renderer's pre-check, the native registry, the turn journal's pruning rule, and — the one nobody had looked at — the process that carries Pi's output events to the screen. Each layer was correct on its own terms. Three of them were changed before the fourth was even noticed.

**A refusal could be correct and still tell you nothing.** Send would go quiet with no sentence at all, or offer itself and then fail with an internal message naming an event route.

## What Changed

### A Journey can work in three places at once

The native registry now tracks work by *conversation* rather than by Journey, and allows each Journey three simultaneous runs out of the machine's four. The fourth attempt inside one Journey is refused as *"This Journey is already running as much work as it can at once"* — **and it names the conversations holding the slots**, by their titles, so you can go to the work that is in the way instead of guessing.

The limit of three is a deliberate reservation, not a technical ceiling: it keeps one slot available for a different Journey so that one busy Journey cannot take the whole machine.

### The event stream reaches the right conversation

Pi's output used to be routed to a Journey. With two conversations working, the second one's output had nowhere to go, and the attempt to start it threw before the turn ever began. Output is now routed to a conversation, so each one receives its own text, its own status and its own completion.

Everything downstream follows from that: each conversation shows its own streaming answer, its own *Working…*, and its own Stop.

### The list says which conversations are working

A conversation that is running carries a **Working** mark beside its title; one that is settling carries **Finishing**. Both are drawn in the same visual register the Journey's own status mark uses, so one reads as a smaller version of the other rather than as a new vocabulary.

Two cases get special handling, because both of them hide running work:

- **A hidden conversation that is working says so on the closed control** — `3 hidden · 1 working`. Hiding is a view preference and must never conceal that work is running.
- **A conversation folded behind *Show N more* does the same.** That one you never chose; the app caps the list at six. Both conceal equally, so both announce.

### A waiting conversation is no longer held shut by a busy sibling

A conversation that had not yet run in the current session was being told it was busy, because it was being handed the status of whichever conversation *was* running. Send stayed disabled, with no explanation, for a conversation doing nothing at all.

This was the last thing standing between the work above and actually being able to use it, and it was found by a field run that was supposed to be a formality.

### Every refusal has a sentence, from one place

Four reasons Send can be unavailable — the registry is still being read, this conversation is already working, this Journey holds all its slots, the machine's Pi capacity is full — now produce their text from a single source, so the Composer and the not-yet-started Journey surface cannot disagree about which refusals deserve words.

A turn journal that is full now explains itself too, instead of returning a code.

## Conscious Exclusions

**The limit is three per Journey and four per machine.** Neither is configurable. The fourth conversation in a Journey is refused with a sentence rather than queued.

**A completed answer can still be invisible until restart.** A turn whose answer was fully written and durable once sat for seventy minutes while the screen said *Working…*; restarting recovered it intact. Nothing was lost, and nothing is fixed here. The mechanism is not established, and it is recorded rather than guessed at.

**A settlement that only succeeds through recovery still writes no timing record.** Known before this release, now measured, and still open. It means the settlement ledger undercounts exactly the turns that needed help.

**Some refusals are still silent.** Send can be unavailable during a recovery inspection or while a conversation reloads, with no sentence. This release unified the *admission* refusals, which is a different set.

**A hung-but-live run still says nothing.** Unchanged, and still recorded.

**Mirror history entries are never marked.** They have no thread that can hold a run, so there is nothing to report.

## What We Learned

**Surveying one path exhaustively is not surveying the system.** Four separate investigations examined the admission path — the registry, its consumers, the runtime state, the journal, the validator — and none examined the event transport. Three slices shipped, each correct, each necessary, and together insufficient. That was discovered in the field rather than in review.

**A field verification can pass for the wrong reason.** The run that was taken as proof of concurrency had, earlier in its sequence, a calibration turn whose only purpose was measuring execution time. That turn happened to run in the same conversation the test's second turn used, and in doing so it quietly satisfied the precondition the test was supposed to be checking. The next run, without it, failed immediately. **A verification should be built so it does not depend on facts it cannot establish** — and this one depended on one nobody had named.

**Removing a thing one step too early costs more than keeping it one step too long.** A constant marking an intermediate state was flipped and deleted in a single change; the field refuted it within one attempt, and there was nothing left to revert. The second time, it was flipped and kept, and only retired once the field produced the evidence. The second ordering cost one line and saved a regression.

**A test that bounds a rule must test the half that can break.** The case guarding the behaviour behind the Send defect used two conversations that *both* had already run — asserting the half that cannot misfire. The entire suite of 1,963 tests passed unchanged when the defect was fixed, which measured the gap rather than arguing about it.

**Two signals at two grains must not share one word.** The conversation list already said *Working…* on its New button, meaning something else entirely. The per-conversation mark had to find its own word rather than add a second meaning to that one.

## Next Horizon

Returning you to the conversation you actually left, which has been owed since the previous release. Then the turn whose answer exists but cannot be seen, and the settlement that succeeds quietly and leaves no record of having done so.
